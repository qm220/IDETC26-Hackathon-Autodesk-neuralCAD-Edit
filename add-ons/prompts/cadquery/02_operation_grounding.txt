You are given:

1. The natural-language edit request.
2. model.json, which follows the Hierarchical CAD Model Ontology:

   Part
   → Section
      → Section Function
      → Section Behavior
      → Feature
         → Feature Function
         → Feature Behavior
         → Relationships with other Features
         → B-rep Faces

3. Multi-view images of the original CAD model.
4. The CAD Operation Grounding Ontology, which defines the controlled
   vocabulary for:
   - edit requests;
   - edit operations;
   - target references;
   - target grounding;
   - parameters;
   - constraints;
   - intended functions and behaviors;
   - unresolved references;
   - affected geometry;
   - operation dependencies;
   - modeling plans and modeling steps.

Your task is to construct an ontology-guided operation.json describing:

1. what the user requested;
2. the separate CAD operations contained in the request;
3. what geometry each operation refers to;
4. how those references resolve to model.json;
5. what remains unresolved;
6. the CAD modeling procedure needed to perform each operation.

Do not invent section IDs, feature IDs, face IDs, solid IDs, dimensions,
or deterministic geometric facts that are not supported by model.json,
the multi-view images, or the request.

Face is the lowest-level B-rep entity represented in model.json and
operation.json.

If a CAD operation later requires lower-level boundary geometry during
execution, derive it programmatically from the grounded face(s) in CadQuery.
Do not introduce additional boundary-level entities into operation.json.


==================================================
STAGE 1 — REQUEST WORDING ANALYSIS
==================================================

Analyze the original request lexically.

Categorize meaningful words or phrases into:

1. ACTION WORDS

Words or phrases describing:
- a CAD modification;
- creation of a new feature;
- removal of geometry;
- modification of existing geometry;
- surface transition/treatment;
- transformation;
- replication;
- assembly or mounting.

2. REFERENCE WORDS

Words or phrases referring to:
- existing sections;
- existing features;
- existing faces;
- new geometry created by another action;
- feature groups;
- interfaces;
- geometric relationships;
- structural relationships.

3. PARAMETER WORDS

Words or phrases expressing numerical or dimensional information such as:
- diameter;
- radius;
- depth;
- length;
- thickness;
- width;
- angle;
- offset;
- count;
- numerical values and units.

4. INTENTION WORDS

Words or phrases describing:
- engineering purpose;
- desired function;
- desired physical behavior;
- desired performance change.

5. RELATIONAL WORDS

Words or phrases that constrain relationships between geometry.

Examples include:
- connecting;
- between;
- through;
- across;
- adjacent;
- aligned;
- concentric;
- coaxial;
- parallel;
- perpendicular;
- surrounding.

These MUST NOT be discarded as grammatical words when they affect geometric
interpretation.

6. GRAMMATICAL WORDS

Articles, conjunctions, auxiliary words, and other words without independent
engineering meaning.


==================================================
STAGE 2 — OPERATION DECOMPOSITION
==================================================

Decompose the request into separate EditOperations.

If multiple modifications are connected using words such as:
- and;
- then;
- also;
- followed by;

represent them as separate operations.

Do not combine geometrically distinct operations into a single action.

For each operation determine:
- operation_id;
- operation_type;
- operation_category;
- operation_description;
- extraction_status.

Use the most specific operation type supported by the Operation Ontology.

Possible categories include:
- add;
- remove;
- modify;
- surface_transition;
- transform;
- replicate;
- assembly;
- design_synthesis.

Examples include:
- AddHoleOperation;
- AddRibOperation;
- AddGrooveOperation;
- AddBossOperation;
- RemoveFeatureOperation;
- ResizeOperation;
- ChamferOperation;
- FilletOperation;
- PatternOperation;
- MountOperation.

Do not invent an additional CAD operation simply because it may be useful
during implementation.


==================================================
STAGE 3 — PARAMETER EXTRACTION
==================================================

For each operation extract every explicitly stated geometric parameter.

For each parameter record:
- name;
- value;
- unit;
- status;
- precision;
- raw_expression.

Parameter status should distinguish:

explicit:
directly stated in the request.

derived:
mathematically or geometrically derived from explicit information.

inferred:
selected through engineering reasoning but not stated by the user.

unspecified:
required for execution but not provided.

Do NOT present an inferred parameter as if it were explicitly requested.


==================================================
STAGE 4 — TARGET REFERENCE EXTRACTION
==================================================

For each operation create a TargetReference describing what the user appears
to refer to BEFORE grounding it to model.json.

Record:
- raw_expression;
- target_level;
- target_feature_type, if identifiable;
- target_face_role, if identifiable;
- qualifiers;
- set_quantifier;
- expected_cardinality;
- resolution_status.

Possible target levels include:
- part;
- section;
- feature;
- feature_group;
- face;
- solid;
- new_geometry;
- new_component.

A target may refer to:
- existing geometry;
- geometry created by a previous operation;
- a relationship between existing features;
- newly synthesized geometry.

Do NOT replace the raw natural-language reference with a model ID.

Preserve both:
1. the original reference;
2. the later grounded target.


==================================================
STAGE 5 — QUALIFIER AND CONSTRAINT EXTRACTION
==================================================

Separate descriptive qualifiers from operation constraints.

QUALIFIERS help identify which geometry is being referenced.

Examples:
- front hole;
- upper mounting face;
- nearest slot;
- corresponding bore;
- hole used for mounting.

Possible qualifier categories include:
- semantic_location;
- cad_location;
- geometric;
- topological;
- relational;
- functional;
- behavioral;
- orientation;
- comparative.

CONSTRAINTS describe how the operation or resulting geometry must relate to
other geometry.

Examples:
- between two holes;
- connecting two holes;
- coaxial with an existing bore;
- mounted from the top;
- aligned with an axis;
- adjacent to a face;
- passing through a section;
- preserving an existing interface.

Record constraints separately with:
- constraint_id;
- category;
- relation;
- subject;
- reference;
- additional_references;
- value;
- unit;
- raw_expression.

Do NOT reduce a meaningful geometric relationship such as "connecting" to a
vague text note.


==================================================
STAGE 6 — INTENDED FUNCTION AND BEHAVIOR
==================================================

Extract engineering intention separately from the geometric operation.

Distinguish:

INTENDED FUNCTION:
What engineering purpose should the modification achieve?

INTENDED BEHAVIOR:
What desired physical/mechanical behavior is stated or implied?

The intention MUST NOT introduce additional geometry not requested by the user.

If an intention is explicitly stated, preserve its original expression.

If it must be inferred, mark the inference with lower confidence.


==================================================
STAGE 7 — UNRESOLVED INFORMATION
==================================================

Before grounding against model.json, identify anything that remains
unspecified or ambiguous.

Possible unresolved information includes:
- unresolved_target;
- unresolved_geometry;
- unresolved_parameter;
- unresolved_orientation;
- unresolved_relationship;
- design_freedom.

For each unresolved item record:
- type;
- raw_expression;
- description;
- candidate_values or candidate_entities if available;
- resolution_rule;
- requires_user_clarification.

Do not guess missing geometry simply to make the operation executable.


==================================================
STAGE 8 — MODEL GROUNDING
==================================================

Use:

1. model.json;
2. multi-view images;
3. parsed TargetReference;
4. operation constraints;
5. intended function and behavior;

to resolve each operation against the original CAD model.

Follow the model hierarchy:

Part
→ Section
→ Feature
→ B-rep Face.

Face is the lowest explicit B-rep grounding level.

Do not jump directly from a natural-language reference to a B-rep face when
higher-level semantic information is available.


--------------------------------------------------
8.1 SECTION GROUNDING
--------------------------------------------------

First identify candidate Sections.

Use evidence including:
- section name;
- section description;
- location;
- section function;
- section behavior;
- associated features;
- semantic orientation;
- multi-view appearance;
- geometric relationships.

If the request explicitly identifies a section, use it directly.

If no section is explicit, use the request intention, feature reference,
relationships, function, and behavior to rank possible sections.


--------------------------------------------------
8.2 FEATURE GROUNDING
--------------------------------------------------

Within candidate Sections, identify candidate Features.

Use:
- feature name;
- ontology feature class;
- feature function;
- feature behavior;
- interface type;
- relationships with other features;
- B-rep faces;
- semantic face roles;
- visual location.

If the request contains a relational expression such as:

"connecting the two holes"

do NOT interpret "connecting" as simply:

"create another hole somewhere nearby".

Resolve:

1. which two hole features are referenced;
2. what relationship "connecting" imposes between them;
3. whether the new geometry should span, intersect, align with, or otherwise
   connect those features.


--------------------------------------------------
8.3 RELATIONSHIP GROUNDING
--------------------------------------------------

Use feature-to-feature relationships from model.json wherever possible.

Examples include:

STRUCTURAL:
- attachedTo;
- adjacentTo;
- sharesBoundaryWith;
- blendsInto.

GEOMETRIC:
- coaxialWith;
- concentricWith;
- parallelTo;
- perpendicularTo;
- alignedWith;
- offsetFrom;
- insideFeature;
- surroundsFeature.

FUNCTIONAL:
- transmitsLoadTo;
- supportsFeature;
- locatesFeature;
- guidesFeature;
- constrainsFeature;
- providesClearanceFor;
- engagesWith;
- mountsTo.

Relationship evidence should be preferred over vague directional language when
it identifies geometry more reliably.


--------------------------------------------------
8.4 ORIENTATION GROUNDING
--------------------------------------------------

If the request uses:
- front;
- back;
- top;
- bottom;
- left;
- right;

use the SEMANTIC ORIENTATION stored in model.json.

Do NOT assume these words correspond to CAD +X, -X, +Y, -Y, +Z, or -Z.

If semantic orientation is unresolved or confidence is low:
- mark the directional reference as ambiguous;
- use feature relationships, geometry, function, and visual evidence instead.


--------------------------------------------------
8.5 FACE GROUNDING
--------------------------------------------------

Once the Feature is identified, inspect its B-rep faces.

Use:
- semantic_role;
- face name;
- surface type;
- dimensions;
- axis;
- centroid;
- bounding box;
- adjacency;
- visual correspondence.

Examples:

"hole"
primarily resolves to a HoleFeature.

"hole wall"
may resolve to a face with semantic role such as bore_wall.

"mounting surface"
may resolve to a face with semantic role such as mounting_face or seating_face.

"existing chamfer"
may resolve to a ChamferFeature and its chamfer_surface face.

"existing fillet"
may resolve to a FilletFeature and its fillet_surface face.

Only use FACE IDs explicitly present in model.json.


--------------------------------------------------
8.6 OPERATIONS REQUIRING BOUNDARY GEOMETRY
--------------------------------------------------

Some CAD operations, including chamfering and filleting, may ultimately require
boundary geometry during CadQuery execution.

Do NOT attempt to represent or identify that lower-level boundary geometry in
operation.json.

Instead:

1. Ground the request to the relevant Section.
2. Ground it to the relevant Feature.
3. Ground it to the relevant FACE or FACE set.
4. Preserve the semantic role of those faces.
5. In the modeling plan, instruct CadQuery to derive the required boundary
   geometry programmatically from the grounded face(s) and their topology.

The VLM is responsible for semantic grounding.

CadQuery is responsible for deterministic boundary extraction during execution.


==================================================
STAGE 9 — GROUNDED TARGET
==================================================

For each operation create a GroundedTarget.

Record:
- part_id;
- section_ids;
- feature_ids;
- feature_group_ids;
- face_ids;
- solid_ids.

Also record:
- resolution_status;
- confidence;
- grounding_evidence.

Possible grounding evidence categories include:
- semantic;
- functional;
- behavioral;
- relational;
- geometric;
- topological;
- visual.

If multiple plausible candidates remain, preserve them as candidate targets
rather than forcing a low-confidence selection.


==================================================
STAGE 10 — OPERATION DEPENDENCIES
==================================================

Determine whether operations depend on each other.

Examples:

AddHoleOperation
→ followed by
AddGrooveOperation applied to the newly created hole.

RemoveFeatureOperation
→ followed by
ChamferOperation applied to geometry exposed by the removal.

Record dependencies such as:
- before;
- after;
- depends_on;
- modifies_output_of;
- uses_output_of.

If an operation targets geometry created by a previous operation, explicitly
record that dependency.


==================================================
STAGE 11 — AFFECTED ENTITIES
==================================================

For each operation identify model entities expected to be:
- modified;
- removed;
- intersected;
- used as construction references;
- topologically affected.

Record:
- section_ids;
- feature_ids;
- face_ids;
- solid_ids.

Affected entities are not necessarily identical to the primary target.


==================================================
STAGE 12 — MODELING PLAN
==================================================

After the operation has been semantically interpreted and grounded, produce a
detailed professional CAD modeling plan.

Do not create the modeling plan before target grounding.

Where relevant include:
- identify datum geometry;
- select reference face or plane;
- create datum plane or axis;
- construct sketch;
- apply dimensions and constraints;
- project/reference existing geometry;
- extrude;
- cut;
- revolve;
- sweep;
- loft;
- boolean union;
- boolean subtraction;
- pattern;
- mirror;
- chamfer;
- fillet;
- assembly placement;
- alignment;
- interference checking;
- geometric validation.

For every modeling step record:
- step_index;
- step_type;
- description;
- section_ids used;
- feature_ids used;
- face_ids used.

If an operation requires boundary geometry that is not explicitly represented
in model.json, instruct the CAD execution stage to derive it from the grounded
face topology.

Do not invent a separate semantic identifier for that boundary geometry.

Do not silently choose unspecified dimensions.

If execution requires a missing parameter:
- identify it as unresolved;
- explain how it should be obtained or derived.


==================================================
STAGE 13 — EXPECTED RESULT AND VALIDATION
==================================================

For each operation describe the expected post-edit result.

Also define validation criteria that can later be used after CadQuery execution.

Possible validation criteria include:
- requested feature exists;
- correct target feature was modified;
- diameter/radius/depth matches request;
- requested relationship is satisfied;
- requested chamfer/fillet or other surface transition exists;
- unintended geometry remains unchanged;
- no unwanted intersections occur;
- requested function or behavior is supported;
- topology remains valid.

These should describe expected outcomes, not introduce new design requirements.


==================================================
FINAL VALIDATION
==================================================

Before returning operation.json verify:

1. Every operation corresponds to something stated or necessarily implied by
   the request.
2. Multiple distinct edits are represented as separate operations.
3. All explicit numerical parameters have been preserved exactly.
4. Inferred parameters are clearly distinguished from explicit parameters.
5. Raw natural-language target expressions are preserved.
6. Every referenced section, feature, face, feature group, and solid ID exists
   in model.json.
7. No FACE ID has been invented.
8. Section grounding follows the semantic hierarchy in model.json.
9. Feature functions and behaviors are used when they provide useful target
   evidence.
10. Feature-to-feature relationships are used to interpret relational wording.
11. Semantic directions are not confused with CAD camera directions.
12. Relational words such as "connecting", "between", "through", and "aligned"
    have not been discarded.
13. Unresolved information is explicitly recorded.
14. Modeling steps are produced only after semantic grounding.
15. Operation dependencies are explicit where one action acts on geometry
    created by another action.
16. Intended engineering function and behavior are kept separate from geometric
    operations.
17. Face is the lowest-level explicit B-rep grounding entity.
18. Lower-level boundary geometry required by CAD execution is derived
    programmatically from grounded faces rather than represented in
    operation.json.
19. The final JSON follows the CAD Operation Grounding Ontology vocabulary and
    hierarchy.
